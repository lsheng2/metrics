## Purpose
Provider Correlation 定义 Jira 与 Intel HSD-ES 作为并行 provider 时如何在 dashboard platform 中建立可解释、可追溯、可撤销的关联。Correlation 的目标是把跨系统事实放在同一个分析上下文里，而不是把不同 provider 的 truth 合并成一个不可审计记录。

## Requirements

### Requirement: Cross-provider correlation model
系统 SHALL 提供 provider-neutral correlation model，用于表达两个或多个 provider work items 之间的 candidate、confirmed、rejected 或 stale relationship。

#### Scenario: Jira and HSD-ES records appear related
- **WHEN** Jira issue 和 HSD-ES record 通过 explicit link、shared external id、title fingerprint、component/release overlap 或时间窗口被判断为可能相关
- **THEN** 系统 SHALL 创建 correlation candidate with evidence、confidence、source、created_at 和 provider item identities，而不是自动合并两个 provider records

#### Scenario: User confirms a relationship
- **WHEN** 用户或 approved policy 确认一个 Jira-HSD-ES relationship
- **THEN** 系统 SHALL mark the correlation as confirmed and preserve the evidence that justified the decision

### Requirement: Provider truth remains separate
Correlation SHALL NOT overwrite provider-native fields or make one provider the source of truth for another provider's state。

#### Scenario: HSD-ES state differs from Jira status
- **WHEN** a correlated HSD-ES record has state `A` and correlated Jira issue has status `B`
- **THEN** dashboard SHALL display both provider-native states and MAY provide a semantic comparison, but SHALL NOT replace either value with the other

### Requirement: Correlation evidence provenance
Every correlation SHALL preserve evidence provenance, including provider id、work item id、field names、matched values、matching method 和 confidence rationale。

#### Scenario: Correlation is generated by matching release and component fields
- **WHEN** system proposes a Jira-HSD-ES correlation based on release target、area/component、owner 或 summary similarity
- **THEN** the correlation payload SHALL include the exact fields and values used for the match

### Requirement: Correlation-aware dashboard consumption
Dashboards SHALL consume correlation artifacts to show cross-provider views such as Jira bug trend plus HSD-ES defect/record state, but SHALL keep calculation ownership explicit。

#### Scenario: Dashboard compares Jira and HSD-ES trends
- **WHEN** dashboard renders a correlated Jira/HSD-ES quality view
- **THEN** it SHALL identify which series comes from Jira facts, which series comes from HSD-ES facts, and which rows are linked by correlation artifacts

### Requirement: Correlation requires HSD-ES API contract confirmation
HSD-ES correlation implementation SHALL use confirmed HSD-ES API details for article identity、tenant、subject、EQL query support、lookup metadata、comment/children/link availability、permission filtering、pagination 和 link/external-id fields。

#### Scenario: HSD-ES tenant-specific rules are not imported
- **WHEN** HSD-ES tenant-specific API rules or target field mappings have not been reviewed
- **THEN** implementation SHALL treat tenant names、subject names、required field rules、field mappings、permission behavior and update capabilities as open questions, and SHALL only implement provider-neutral assumptions plus confirmed generic HSD-ES REST/EQL mechanics
